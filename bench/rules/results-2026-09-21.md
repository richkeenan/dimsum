# Compact index measurements — 2026-09-21

Apple M4, 10 CPUs, 32 GiB, macOS 15.6, darwin/arm64, Go 1.26.8, default GC.
Deterministic synthetic fixtures described in [README](README.md). Ten repetitions,
100 ms target per benchmark; build calibration may execute one or more builds.
Benchmarks run without concurrent test/fuzz workloads. These are Mac results.

Commands (the working-set benchmarks were added after the initial complete run):

```sh
go test ./internal/policy -run '^$' -bench . -benchmem -benchtime=100ms -count=10
go test ./internal/policy -run '^$' -bench 'BenchmarkSuffixCandidates|BenchmarkSnapshotWorkingSet' -benchmem -benchtime=100ms -count=10
```

### Candidate selection

| Keys | Exact hash 70% B/key | Exact hash 80% B/key | Reversed sorted B/key | Suffix hash-walk 70% ns | Suffix hash-walk 80% ns | Reversed sorted suffix ns |
|---|---:|---:|---:|---:|---:|---:|
| 80k | 50.30 | 47.44 | 36.25 | 68.00 | 120.25 | 356.65 |
| 250k | 49.86 | 47.00 | 35.78 | 54.44 | 116.65 | 374.40 |
| 1m | 48.68 | 45.82 | 34.27 | 75.06 | 137.25 | 420.70 |

Candidate B/key includes index capacities and complete keys, **excludes all
provenance**. The 1m suffix ranges were 51.99–166.20 / 101.80–229.50 /
414.00–443.20 ns, respectively. Random hash seeds produce probe variation.
Single hot-name hash misses varied even more by bucket, so they were not used
alone to select the load factor.

Selected:

- **Exact hash at 70%**: hot exact hits ~6.6 ns, versus ~83–94 ns for the sorted
  candidate. 80% saved only ~2.86 B/key and had worse working-set probe costs.
- **Sorted reversed-label suffix index**: chooses smaller storage over the
  faster hash-and-suffix-walk alternative. At 1m it saves 14.41 B/suffix key
  against 70% hashing (29.6% of that index; ~7.2 MB for a half-suffix 1m snapshot),
  at ~346 ns extra candidate lookup cost on the measured mix. The complete
  snapshot still measured ~455 ns on its mix. This is an explicit memory/speed
  tradeoff, not a claim that sorted lookup is fastest.

A compressed radix trie/LOUDS/automaton and probabilistic filters were not
implemented or measured. The selected reversed-label index is sorted and
offset-based, not a compressed radix tree. They remain possible later work.

The entire initial benchmark command, including the reference matcher, took
101.25 seconds and `/usr/bin/time -l` reported 1,309,704,192 bytes maximum RSS.
That command-wide RSS is not a per-snapshot number. `.Memory()` and `MaxBytes`
are retained-payload accounting, not hard process/build caps. Admission must
include input, active/retired snapshots, compiler temporaries and GC garbage.

Separate fresh benchmark processes then measured RSS for each size using a
compiled test binary and ten single-build repetitions:

```sh
go test -c ./internal/policy -o /path/to/policy.test
/usr/bin/time -l /path/to/policy.test -test.run '^$' -test.bench '^BenchmarkSnapshotBuild$/^1000000$' -test.benchtime=1x -test.count=10
```

Replace `1000000` with each size. Process maximum RSS was **80,969,728 /
230,260,736 / 864,075,776 bytes** for 80k / 250k / 1m. Corresponding sampled
heap peak ranges were 60.983–63.232 / 192.968–209.047 / 783.979–831.967 MB.
Build-time medians were 48.78 / 168.21 / 749.79 ms. These include input, active
snapshot, construction and process/runtime storage, not only the new index.
